PURPOSE
=======

This document records the BR2 interface work that has been physically tested.

The goal is simple:

    Make sure the FPGA can drive known signals out through the BR2 connector
    before we route additional address-decoder signals there.

Think of BR2 as a doorway.

Before sending important signals through the doorway, we first sent a simple
1 kHz square wave through it so we could prove the physical path worked.

That test passed.

We are now beginning to replace individual diagnostic outputs with real
address-decoder signals.

The development rule is:

    Change one signal.

    Build it.

    Load it.

    Measure it.

    Verify it.

    Document it.

    Then move to the next signal.

###############################################################################
1 kHz SQUARE-WAVE GENERATOR
###############################################################################

The FPGA clock is:

    100 MHz


That means the FPGA receives:

    100,000,000 clock cycles every second.


The BR2 diagnostic counter counts from:

    0

through:

    49,999


That is:

    50,000 FPGA clock cycles.


At 100 MHz:

    50,000 clock cycles = 500 microseconds


Every 500 microseconds the signal changes state:

    LOW  -> HIGH

or

    HIGH -> LOW


A complete square-wave cycle requires two state changes:

    LOW -> HIGH -> LOW


Therefore:

    500 microseconds HIGH

    500 microseconds LOW


Total period:

    1 millisecond


Frequency:

    1 / 0.001 second = 1000 Hz


Therefore:

    BR2 TEST FREQUENCY = 1 kHz


The 1 kHz diagnostic waveform is currently routed to:

    B41


It is no longer routed to B42.


###############################################################################
CURRENT LUCID IMPLEMENTATION
###############################################################################

The diagnostic logic uses two registers:

    br2_counter

and

    br2_square


The counter stores how many 100 MHz FPGA clock cycles have occurred.

The square-wave register stores the current output state.


Simplified operation:

    Start counter at 0.

    Count upward every FPGA clock.

    When counter reaches 49,999:

        Reset counter to 0.

        Toggle br2_square.

    Repeat forever.


The diagnostic output assignment is:

    br2_test = br2_square.q


Therefore:

    B41 = 1 kHz square wave


The ROM output assignment is:

    br2_probe2 = rom_cs_n


Therefore:

    B42 = ROM active-low chip select


These signals intentionally perform different functions.

B41 remains the known-good diagnostic reference.

B42 now verifies the actual ROM decoder output.


###############################################################################
ROM CHIP-SELECT LOGIC
###############################################################################

The ROM chip-select signal inside the FPGA is:

    rom_cs_n


The "_n" suffix means:

    ACTIVE LOW


The ROM decode equation is:

    rom_cs_n = y[4] & y[5] & y[6] & y[7]


The y signals come from the LS138 decoder logic.


When the address is outside the ROM region:

    rom_cs_n = HIGH


Therefore:

    B42 = HIGH


When the address is inside the ROM region:

    rom_cs_n = LOW


Therefore:

    B42 = LOW


The hardware test at address:

    0x8000

produced:

    B42 = 0 V


This confirms that the ROM select became active.

###############################################################################
BR2 DEVELOPMENT RULE
###############################################################################

Do not change several BR2 signals at the same time.

Recommended procedure:

    1. Keep one known-good 1 kHz probe signal.

    2. Replace only one BR2 test signal with a real project signal.

    3. Run the project checker.

    4. Build the FPGA project.

    5. Load the FPGA.

    6. Measure the new signal.

    7. Regression-test the existing decoder.

    8. Update the documentation.

    9. Check Git status.

    10. Commit only after the hardware test passes.


This gives us a known-good reference signal while new BR2 signals are added.
